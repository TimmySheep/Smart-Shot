# Smart Shot：原生 macOS 智能截图 App 开发任务书

**项目类型：** macOS 原生桌面工具

**工作名称：** Smart Shot（暂定，可后续修改）

**技术栈：** Swift + SwiftUI + ScreenCaptureKit

**开发模式：** 独立项目、分阶段实现、本地处理、真实功能优先

**最高原则：** 截图质量与可靠性优先于截图数量和运行速度。

## 一、项目目标

开发一款轻量、精致、接近 App Store 版 Auto Shot 使用体验的 macOS 智能截图工具。

软件需要能够持续观察用户选定的屏幕或应用窗口，通过本地图像分析识别画面变化，在适当时机自动保存高分辨率截图。

与传统定时截图不同，本项目希望实现：

1. 画面发生重要变化时，及时保存截图。
2. 画面长期稳定时，减少不必要的截图。
3. 通过定时保底机制避免长时间没有保存画面。
4. 对短暂出现的内容尽可能及时捕获。
5. 对公式、文字、图表和手写批注采用保守策略。
6. 所有判断尽可能在本地完成，不依赖云端 AI。
7. 保存的原始截图能够直接用于现有考研笔记工作流。

**本项目不是简单复刻 Auto Shot，也不是在现有笔记工作流里增加一个脚本，而是一款具有独立 UI、独立设置、独立截图引擎的原生 macOS App。**

## 二、设计要求

请使用本任务书附带的 Smart Shot 界面设计图作为视觉参考。

设计图包含主界面、运行界面、设置、截图历史、菜单栏和截图示例。它是视觉方向参考，不要求机械复制每个像素。

### 2.1 视觉风格

尽可能接近 Auto Shot 的轻量、简洁、原生 macOS 风格。

具体要求：

- 使用 SwiftUI 原生控件。
- 浅色主题优先，支持系统外观。
- 合理利用系统字体、留白、圆角、分隔线和系统图标。
- 不使用过多卡片、渐变、装饰性图形或复杂动画。
- 主界面打开后，应当能立即开始或停止截图。
- 高级设置放在独立设置窗口，不要堆满主界面。
- 运行状态、截图数量、最后一次截图时间清晰可见。
- 遵循 macOS 常见交互习惯，支持键盘操作和合理的窗口尺寸。

不要设计成网页后台、Electron 管理面板或复杂的监控仪表盘。

### 2.2 主窗口

主窗口至少包括：

- App 图标与名称。
- 当前监控目标。
- 选择窗口或屏幕。
- 智能模式 / 定时模式切换。
- 保底截图间隔。
- 当前运行状态。
- 截图保存目录。
- 开始截图 / 停止截图按钮。
- 最近截图事件列表。
- 设置入口。

运行时显示：

- 已运行时长。
- 已保存截图数量。
- 最近一次截图时间。
- 最近一次触发原因。
- 当前检测状态。
- 权限或异常提示。

### 2.3 设置界面

至少包含：

**通用设置**
- 开机或登录时启动（可选）。
- 关闭窗口时是否继续后台运行。
- 是否显示菜单栏图标。

**截图设置**
- 定时截图间隔。
- 智能检测灵敏度。
- 检测帧率。
- 触发冷却时间。
- 连续动态画面处理策略。
- 输出图片格式。

**保存设置**
- 保存目录。
- 自动按日期组织文件夹。
- 文件命名规则。
- 磁盘空间不足时的处理方式。

**高级设置**
- 忽略区域（可选）。
- 本地检测参数。
- 诊断日志。
- 恢复默认设置。

第一版不需要账户系统、云端同步、订阅付费、AI 对话或复杂的素材管理功能。

## 三、核心功能与实现要求

### 3.1 屏幕与窗口选择

使用 ScreenCaptureKit 获取可用屏幕、应用窗口及其必要元数据。

要求：

- 用户可以选择指定应用窗口或显示器。
- 尽可能提供窗口预览、应用名称和分辨率信息。
- 明确显示当前监控对象。
- 支持目标窗口关闭、消失或切换后的异常处理。
- 正确处理 macOS 屏幕录制权限。
- 权限不足时给出明确说明和系统设置入口。
- 不得在未经用户授权的情况下持续采集屏幕。

尽量让 App 只处理用户指定的目标，而不是无必要地采集整个桌面。

### 3.2 定时截图模式

保留传统定时截图作为基准方案。

支持可配置的截图间隔，例如 10、15、30、60 秒及自定义间隔。

该模式必须可以独立工作，不依赖智能检测算法。

它同时用于与智能模式进行对照测试。

### 3.3 智能截图模式

这是项目的核心。

通过 ScreenCaptureKit 获取连续画面，在内存中执行轻量级图像分析，决定是否保存截图。

优先使用已有研究中的本地图像变化算法：

- 低分辨率图像比较。
- 灰度差异。
- 感知哈希或等价轻量特征。
- 局部区域变化检测。
- 变化持续性判断。
- 触发阈值与冷却策略。
- 定时保底。

可以参考现有视频实验的局部区域检测配置，但必须根据真实输入尺寸、图像归一化方式和参数定义核实后再使用，不能直接照抄数字。

**检测到画面发生变化，不等于已经证明画面包含新的教学信息。**

因此，应尽可能结合局部变化和时间持续性减少鼠标、动画噪声等引起的无意义截图，同时保留无法确定的变化。

不要在第一版引入复杂的云端模型来判断每一帧是否重要。

### 3.4 定时保底机制

智能模式必须提供独立可配置的保底间隔。

例如，每隔一定时间保存一张截图，即使检测器没有发现变化，也不会无限期停止保存。

保底间隔是可调参数，不是“绝对不会漏拍”的保证。

建议设置 10、15、30、60 秒等选项。

由于当前算法仍有短暂内容漏检的情况：

- 初次运行应明确标注为实验性智能截图。
- 允许用户选择保守的短间隔。
- 不得默认宣称 30 秒或 60 秒保底已经足以替代原有截图策略。
- 运行过程中必须记录保底截图与事件触发截图的区别。

### 3.5 短暂内容保护与高分辨率保存

这是本项目最重要的工程难点之一。

不能仅在低分辨率检测器发现变化后，再临时请求高清截图，并假定重要内容一定还在。

请设计有限大小的内存帧缓冲区，保存最近一段时间已经捕获的画面，以便在触发时选择最能体现变化的有效帧。

要求：

- 原始截图以高分辨率保存。
- 检测图片和最终保存图片分开处理。
- 内存缓冲区有明确的大小或内存预算。
- 不将每一帧写入磁盘。
- 记录触发时间与实际保存帧的时间差。
- 尽可能捕获持续时间较短的画面变化。
- 缓冲区溢出或处理延迟时不得静默丢弃重要事件。
- 如果无法保证捕获，必须在日志中明确记录。

初期可评估每秒 1、2、5 帧等检测频率，根据 CPU、内存和漏检测试决定实际默认值。

不要把某个帧率预先认定为最佳值。

### 3.6 连续动态画面处理

电影理论课程可能播放影片，因此必须考虑持续变化的视频画面。

如果对每次镜头变化都立即截图，可能出现截图数量激增。

请设计一个可配置的动态画面处理策略：

- 识别持续高频变化的画面。
- 避免因每一帧变化而无限触发截图。
- 提供适当的定时采样选项。
- 对视频开始、结束、字幕变化和重要场景切换尽可能保留事件。
- 记录因冷却、限频或合并而未单独保存的候选事件。

不能把电影片段简单当成无关动态背景。

第一版如果无法可靠识别所有重要电影镜头，应明确说明限制，并提供较保守的采样模式。

### 3.7 截图文件保存

默认优先采用 PNG 无损格式。

建议目录结构：

`用户选择的目录/SmartShot/YYYY-MM-DD/`

文件名至少包含：

- 日期。
- 时间。
- 毫秒或其他足以避免重名的序号。
- 可选的触发原因。

每张截图都应记录必要的元数据：

- 实际截图时间。
- 目标窗口或显示器标识。
- 图片分辨率。
- 触发原因。
- 使用的检测参数。
- App 版本。
- 图片文件名。
- 文件 SHA-256（适合在保存完成后计算）。

另外维护一份可追加的 JSONL 事件记录，记录：

- 检测事件。
- 保存事件。
- 保底事件。
- 被抑制或合并的事件。
- 权限异常。
- 运行异常。

元数据应能支持未来考研笔记工作流追溯图片来源。

不能修改、覆盖或删除其他软件已经保存的截图。

## 四、技术架构

请采用清晰、可测试、可独立演进的模块化设计。

建议划分如下：

1. **App UI**
   - SwiftUI 主窗口。
   - 设置窗口。
   - 菜单栏控制。
   - 截图历史与运行状态。

2. **Capture Service**
   - ScreenCaptureKit。
   - 窗口和屏幕选择。
   - 屏幕捕获权限。
   - 流生命周期与异常恢复。

3. **Frame Analyzer**
   - 图像降采样。
   - 灰度或感知特征。
   - 局部区域变化。
   - 变化置信度。
   - 检测耗时统计。

4. **Capture Policy**
   - 智能触发。
   - 定时保底。
   - 触发冷却。
   - 连续动态画面处理。
   - 异常回退策略。

5. **Frame Buffer**
   - 有界内存缓冲。
   - 时间戳管理。
   - 过期帧清理。
   - 内存上限保护。

6. **Capture Writer**
   - 高分辨率 PNG。
   - 唯一文件名。
   - 事件元数据。
   - 安全写入。

7. **History & Diagnostics**
   - 截图列表。
   - 触发原因。
   - 运行日志。
   - 资源消耗统计。

模块间通过明确接口通信，避免把截图、检测、文件写入和 UI 全部塞进一个 View。

优先使用系统自带框架。只有在确实有必要时才引入第三方依赖。

## 五、质量与性能要求

本项目必须使用可复现的离线测试，而不是只通过人工打开窗口确认功能正常。

### 5.1 图像检测测试

至少准备以下测试场景：

- 两张完全相同的图像。
- 只有鼠标位置不同。
- 播放器进度条变化。
- 文字发生变化。
- PPT 整页切换。
- 公式局部变化。
- 手写批注出现。
- 图表局部变化。
- 一秒左右的短暂画面。
- 连续动态视频。
- 窗口缩放。
- 目标窗口消失。

测试应分别检查是否正确触发、是否出现不必要的截图，以及是否存在漏检。

### 5.2 视频回放验证

使用现有智能截图研究中的视频与检测代码作为参考。

如果可以安全复用已有实验脚本，应先检查依赖和接口，再决定是否复用。

至少验证：

- 检测器按时间顺序工作。
- 不使用未来画面决定过去的截图。
- 记录实际保存帧的时间戳。
- 统计短暂画面漏检。
- 统计无效截图。
- 比较不同检测帧率与阈值。

不得把旧研究的离线最佳结果直接当作新 App 的实际表现。

### 5.3 资源与稳定性

在真实运行环境中记录：

- CPU 使用率。
- 内存占用。
- 检测耗时。
- 图片写入耗时。
- 连续运行时的内存增长。
- 检测事件数量。
- 最终截图数量。

特别检查：

- 连续运行至少 30 分钟。
- 目标窗口关闭与重新打开。
- 屏幕录制权限被撤销。
- 电脑休眠和唤醒。
- 磁盘空间不足。
- 文件写入失败。
- 捕获流异常退出。

不要预先声称已经满足性能目标，必须提供实测数据。

## 六、与现有 Auto Shot 和笔记工作流的关系

第一版必须是完全独立的 App。

- 不修改 Auto Shot。
- 不接管 Auto Shot 的输出目录。
- 不直接接入 V6。
- 不修改现有课程截图、OCR、视觉识读结果或笔记。
- 不调用云端模型。
- 不自动删除重复截图。

建议先让 Smart Shot 与 Auto Shot 并行运行，输出到各自独立目录。

之后再利用真实课程资料比较两种采集策略的截图数量、重要内容召回率、短暂页面漏检及运行资源。

只有通过独立验证，才考虑将其正式用于考研笔记工作流。

## 七、实施阶段

### 阶段 1：项目初始化与界面

- 检查开发环境与现有项目目录。
- 创建独立的原生 macOS 项目。
- 实现主窗口和设置窗口。
- 实现窗口选择、输出目录选择和基本状态显示。
- 建立清晰的模块结构。

验收：应用能够编译启动，界面与参考设计方向一致。

### 阶段 2：定时截图

- 接入 ScreenCaptureKit。
- 实现屏幕和窗口选择。
- 实现定时截图。
- 保存高分辨率 PNG。
- 实现基本日志和权限错误提示。

验收：定时模式能够独立稳定工作。

### 阶段 3：本地智能检测

- 接入图像分析。
- 实现局部变化检测。
- 实现智能触发和保底。
- 实现有限内存帧缓冲。
- 实现触发原因记录。

验收：通过基础图像测试和离线视频回放。

### 阶段 4：设置、历史与后台运行

- 完成菜单栏控制。
- 完成截图历史。
- 完成参数设置。
- 完成后台运行与异常恢复。
- 完成连续动态画面的基础策略。

验收：核心操作均可在 UI 中完成，不需要手动运行脚本。

### 阶段 5：质量与性能验证

- 执行完整离线测试。
- 执行连续运行测试。
- 检查图片来源和时间戳。
- 统计资源消耗。
- 生成与 Auto Shot 对照所需的实验报告。

验收：明确列出已验证能力、尚未验证的风险以及推荐的运行参数。

## 九、完成标准

只有在以下条件得到验证后，才可以称为第一版原型完成：

- App 能正常启动。
- 用户能够选择目标窗口或屏幕。
- 定时截图功能可用。
- 智能检测功能可用。
- 高分辨率图片能够正确保存。
- 保底机制可用。
- 触发原因与时间戳能够追溯。
- 运行中断和异常不会导致静默失败。
- 核心离线测试通过。
- 没有修改 Auto Shot 或 V6。
- 尚未解决的漏检风险已明确记录。

**本项目不以截图减少比例作为唯一成功指标。任何降低截图数量的优化，都必须同时报告它对重要内容捕获的影响。**
